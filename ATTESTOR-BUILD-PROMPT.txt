1. WHAT THE BUSINESS IS
================================================================================

Attestor Security is a security audit firm operating out of India, serving both
Indian and international clients. Solo founder to start, 2–3 people within a
year. It sells:

  - Web application and API security assessments
  - Cloud configuration and posture reviews (AWS, Azure, GCP)
  - Mobile application assessments (Android, iOS)
  - LLM / AI application red teaming
  - Compliance-attached testing (ISO 27001 A.8.8, SOC 2, PCI DSS 11.4, DPDP)
  - Continuous testing retainers and fractional security leadership

The product the client actually buys is a REPORT: independent, evidence-backed,
methodology-named, acceptable to an ISO/SOC 2 auditor and to an enterprise
buyer's procurement team. Everything you build exists to produce that report
faster and more consistently, and to sell it.

Business rules that constrain the software:

  - Attestor is NOT CERT-In empanelled. The software must never state, imply
    or template any claim of empanelment, accreditation or certification the
    firm does not hold.
  - Testing without signed, scoped, in-window authorisation is a criminal
    offence in India (IT Act s.66) and similar elsewhere. The platform must
    make unauthorised testing structurally impossible, not merely discouraged.
  - The firm holds client credentials and client data. It is a data processor
    under India's DPDP Act. Evidence retention, deletion and access control are
    product features, not nice-to-haves.
  - Money is tight. Every component must be free or open source, self-hosted
    where sensible, and must run on a single modest VPS at the start.

2. NON-NEGOTIABLE ENGINEERING RULES (APPLY TO EVERY MODULE, BOTH DELIVERABLES)
================================================================================

Write code the way a senior engineer with fifteen years of production experience
writes it when they are tired and want it to still work in three years.

CODE STYLE

  - Do not write code that looks machine-generated. No ceremonial wrappers, no
    "helper" files containing one function, no interfaces with a single
    implementation, no factories for one product, no config objects for values
    that never change, no defensive try/catch that swallows and logs.
  - Simple beats clever. If it can be done with the standard library, an
    already-installed dependency, or ten lines, do that. Never add a dependency
    for something a few lines cover.
  - No redundant code. Before writing a function, check whether one already
    exists in the repo. Reuse it. Duplication is the most common failure of
    generated code — do not commit it.
  - Comments: short, meaningful, and only where the code cannot explain itself
    (a non-obvious protocol detail, a legal constraint, a deliberate shortcut,
    a known ceiling). Never write a comment that restates the line below it.
    Never write banner comments or section-divider comment art.
  - Naming: camelCase for variables and functions, PascalCase for types and
    classes, SCREAMING_SNAKE for true constants. Human-readable words. No
    leading underscores anywhere, ever. No Hungarian notation, no `data2`,
    no `mgr`, no `utils` dumping ground, no clever abbreviations. A name should
    read as English: `runScanForEngagement`, not `execScanEng`.
  - File names: kebab-case. One clear responsibility per file.
  - No `any` in TypeScript. Strict mode on. No `@ts-ignore` without a comment
    naming the exact reason.
  - Errors: fail loudly and early at trust boundaries. Validate all external
    input (HTTP bodies, YAML policies, tool output) with a schema at the edge,
    then trust it internally.
  - Deliberate simplifications get a one-line comment naming the ceiling and
    the upgrade path, e.g. `// single worker process; shard by engagement if
    concurrency exceeds ~20`.

TESTING

  - Everything with logic gets a test. Not a test suite per function — the
    smallest runnable check that fails if the logic breaks.
  - The scope guard (B6) gets property-based/fuzz tests. It is the one
    component whose failure is a criminal exposure. Test it like it matters.
  - Scanner integration tests run against locally hosted deliberately
    vulnerable applications in Docker (OWASP Juice Shop, DVWA, WebGoat, VAmPI,
    crAPI, and a purpose-built vulnerable LLM app you write). NEVER against any
    internet host, in CI or otherwise.
  - Report rendering gets golden-file tests: fixed findings fixture in, byte-
    stable HTML out, plus one PDF smoke test.
  - CI runs lint, typecheck, unit, integration. Green before merge.

RESEARCH

  - Today is August 2026 and your training data may be stale. Search the web
    before you pin any tool version, CLI flag, output schema, API shape, cloud
    provider testing policy, pricing figure, or standard version number.
  - Sources worth reading: official tool documentation and GitHub repos, OWASP
    project pages (WSTG, ASVS, MASVS, Top 10, LLM Top 10, API Top 10), the
    OWASP Cheat Sheet Series, PortSwigger Web Security Academy, NIST SP 800-115,
    FIRST CVSS specification, HackerOne/Bugcrowd public disclosure reports,
    r/netsec, r/AskNetsec, r/cybersecurity for practitioner sentiment on what
    actually finds bugs versus what wastes hours, and published sample pentest
    reports from established firms to calibrate report quality.
  - Verify current versions before pinning. As of writing: OWASP ASVS 5.0
    (May 2025, ~350 requirements, 17 chapters), OWASP Top 10:2025 (Broken Access
    Control still #1, expanded supply chain coverage), OWASP WSTG (check current
    stable), MASVS 2.x, OWASP LLM Top 10 (prompt injection #1), CVSS 4.0 from
    FIRST — note that many 2026 report templates in the wild still use CVSS 3.1,
    so support BOTH and let the user choose per engagement.
  - When you learn something non-obvious from research, record it in
    `RESEARCH-NOTES.md` with the source URL and date. That file is a deliverable.

WHAT TO NEVER DO

  - Never write code that scans, probes or connects to a target that has not
    passed the scope guard.
  - Never implement denial-of-service, stress, flood or volumetric testing.
    AWS and Azure prohibit it outright. There must be no code path that can do
    it, not even behind a flag.
  - Never implement destructive payloads: no DROP/DELETE/UPDATE without WHERE in
    SQLi verification, no file deletion, no account deletion, no password
    changes, no mass data extraction, no shell persistence.
  - Never store raw client personal data as evidence. Masking is applied at
    capture time, not at report time.
  - Never log credentials, session tokens, API keys or authorisation headers —
    not at debug level, not in error traces, not in tool stdout that gets
    persisted. Build a redaction filter and route every persisted log through it.
  - Never ship a hardcoded secret, key, token or password.
  - Never send client data to a third-party AI provider unless that engagement
    has an explicit `aiAssistEnabled` flag set true by a human, and even then
    only redacted findings text, never raw evidence.
  - Never auto-publish, auto-email or auto-share a report. A human releases it.
  - Never invent a finding, a CVE, a CVSS vector, a reference URL or a client
    quote. If the AI-assist layer cannot ground a sentence in captured evidence,
    it must leave the field empty for the human.
  - Never include cracked, pirated or licence-violating tools.

PART B — THE INTERNAL PLATFORM ("ATTESTOR CONSOLE")
================================================================================

B1. WHAT IT IS AND WHAT IT IS NOT

It IS: a single-tenant-per-deployment engagement orchestration system that
takes a signed scope, runs the right tools automatically, normalises and
deduplicates findings, supports the human tester's manual work, and produces a
professional-grade report, retest report and attestation letter — then keeps
retainer clients continuously monitored.

It IS NOT: an autonomous hacker, a product sold to customers in v1, a
replacement for the tester's judgement, or a general-purpose vulnerability
management platform. Business logic flaws, access-control chains and impact
judgement are human work; the platform's job is to make everything around that
work take minutes instead of days.

Design principle to hold throughout: AUTOMATION IS THE MARGIN, NOT THE PRODUCT.

B2. ARCHITECTURE

  Console (Next.js)  ──►  API (Fastify)  ──►  Postgres
                                │
                                ├──►  Redis + BullMQ  ──►  Workers
                                │                            │
                                │                            ├─► Docker: tool containers
                                │                            └─► MinIO: evidence objects
                                │
                                └──►  Report renderer (Playwright → PDF)

  - Workers execute one job per tool run, in a pinned Docker container, with a
    per-engagement network namespace and a fixed egress IP.
  - All tool output is written to MinIO raw, then parsed by an adapter into the
    normalised finding model. Raw output is retained for defensibility.
  - Everything is queue-driven and resumable. A crashed worker must not lose an
    engagement's progress; jobs are idempotent and re-runnable.

B5. ENGAGEMENT LIFECYCLE (state machine — enforce it, do not allow shortcuts)

  draft
    → scoped              scope items entered
    → authorised          signed authorisation uploaded, signer recorded,
                          validity window set        [GATE: no scanning before]
    → advancePaid         50% received (manual flag)  [GATE: configurable]
    → readyToRun          credentials verified, safety checklist ticked
    → running             jobs executing
    → triage              automated results in, human validating
    → manualTesting       human-led phase, manual findings entered
    → reportDraft         report generated, human editing
    → reportReview        internal review checklist complete
    → released            final payment flagged, report released to client
    → retestPending       within 30 days
    → retestComplete      retest report + attestation issued
    → closed              evidence purged, deletion confirmation sent

Every transition writes to auditLog with actor, timestamp and reason. Backwards
transitions are allowed but must carry a reason string.

B6. SCOPE GUARD AND AUTHORISATION — THE MOST IMPORTANT COMPONENT

This is the component that keeps the founder out of court. Build it first, test
it hardest.

Rules:

  - No tool container may be launched except through `runToolForEngagement`,
    which calls the scope guard first. There must be no second path. Enforce it
    with a single choke point and a lint rule or architectural test that fails
    the build if `docker run` / dockerode is called anywhere else.
  - The guard checks, for every target string and every resolved IP:
      1. an `authorisation` row exists for the engagement, is signed, not
         revoked, and `now` is inside `validFrom..validUntil`
      2. the engagement is in a state permitting execution
      3. the target matches an `included` scopeItem
      4. the target matches NO `excluded` scopeItem
      5. after DNS resolution, the resolved IPs are still in scope — this
         defeats a scoped hostname that resolves to a third party's
         infrastructure or a shared host
      6. the target is not in the global never-touch list: RFC1918 ranges the
         firm does not own, localhost, cloud metadata endpoints (169.254.169.254
         and equivalents), known government/regulator/bank domains, the firm's
         own infrastructure, and any address supplied by the owner as banned
      7. the current time is inside an allowed testing window from the policy
      8. redirects and discovered links are re-checked before being followed —
         crawling must not walk out of scope
  - Failure returns a typed refusal with the exact rule that failed, writes to
    auditLog, and aborts the run. It never "warns and continues".
  - Wildcard scope (`*.example.com`) must be handled explicitly and must never
    silently match `exampleXcom` or a suffix trick. Write the fuzz tests.
  - A `panicStop` control halts every running job for an engagement, or for the
    entire platform, within seconds. Expose it as a prominent console button
    and a CLI command. Log who pressed it.
  - Authorisation upload flow: PDF stored in MinIO, signer name/role/email
    recorded, asset list parsed and diffed against entered scope items with any
    mismatch surfaced for human resolution before the state can advance.
  - Third-party asset warning: if a scope item resolves to shared hosting, a
    SaaS provider or a CDN, surface a blocking prompt that the client's consent
    may not cover that infrastructure and require an explicit acknowledgement
    with a note.
  - Cloud provider policy check: before cloud or infrastructure runs, show the
    provider's current testing policy summary and require acknowledgement. AWS
    permits customer testing on a defined service list and requires a Simulated
    Events form for covert simulations or C2; DoS/DDoS simulation is prohibited
    on AWS and Azure under all circumstances. Search for the current policy text
    and store the acknowledgement.

B7. CREDENTIALS AND AUTHENTICATION PROFILES

This is the part the owner asked about specifically: how the client's
credentials get into the system, and how pre-login versus post-login testing is
controlled.

HOW CREDENTIALS ARRIVE

  - The console generates a one-time, expiring intake link for the engagement.
    The client opens it and submits credentials directly into the vault. The
    credentials never travel through email, WhatsApp or a ticket.
  - Values are encrypted at rest with libsodium secretbox (or age); the key
    comes from the environment/KMS and is never in the database or the repo.
    Decryption happens only inside a worker, in memory, at run time.
  - Every credential set carries a role name, an expiry, and a
    `lastVerifiedAt`. Expired sets block the run with a clear message.
  - A redaction filter sits on every log sink. Credential values, tokens,
    cookies and Authorization headers are replaced before anything is persisted
    or shown in the console.
  - On engagement close, credential rows are cryptographically shredded (key
    material for that engagement destroyed) and the client is told, in the
    closure email, to rotate the accounts anyway.

AUTHENTICATION PROFILE TYPES (the system must support all of these)

  none                unauthenticated / pre-login testing only
  formLogin           username + password on an HTML form
  scriptedLogin       a Playwright script recorded/authored for complex flows
                      (multi-step, captcha-exempt test account, device trust
                      prompts, tenant selection)
  otpAssisted         a login requiring an OTP — support a manual "tester
                      supplies the code" pause, and a shared-secret TOTP option
                      when the client provides one for a test account
  oauth2              client credentials, authorization code with a static test
                      account, refresh token handling
  apiKey              header, query or custom scheme
  bearerJwt           static token, or a token minted by a token endpoint,
                      with automatic refresh before expiry
  sessionCookie       raw cookie jar import for awkward legacy apps
  mtls                client certificate

Each profile stores: how to authenticate, how to DETECT that the session is
still valid (a logged-in indicator: a selector, a URL, a response header, a
JSON field), and how to re-authenticate when it is not. Session death mid-scan
is the single most common cause of a worthless authenticated scan — detect it,
re-auth, and mark the affected requests for re-run.

PRE-LOGIN VS POST-LOGIN TESTING

The policy selects one or both phases explicitly:

  phases:
    preLogin:   run unauthenticated recon, discovery, and all checks that do
                not require a session. Establishes what an anonymous attacker
                sees. Always run this first.
    postLogin:  run authenticated crawling and checks per role.

  For postLogin, the system must:
    - crawl separately per role, keeping per-role site maps
    - maintain one browser context per role so sessions never leak
    - exclude dangerous actions from the crawl: logout, delete account, change
      password, change email, payment submission, mass-delete, invite-user, and
      any path the policy lists under `forbiddenActions`. Default this list
      conservatively and let the policy extend it.
    - respect a `readOnlyMode` that suppresses every state-changing request
      (used for the first pass on production systems)

AUTHORISATION / ACCESS-CONTROL MATRIX TESTING (high-value, automatable)

Build this properly — it is where real findings live and it is the part of
IDOR hunting that machines can genuinely do:

  - Record the request corpus per role during authenticated crawling.
  - For each recorded request from role A, replay it with role B's session,
    with an unauthenticated session, and with the identifier fields mutated
    (adjacent IDs, other tenants' IDs captured during the crawl, UUID swaps).
  - Compare responses using a similarity heuristic (status, length, structure,
    key fields) rather than exact match, and flag any case where a lower
    privilege receives substantially the same content as a higher one.
  - Present these as CANDIDATES in a human review queue, never as confirmed
    findings. The human confirms and writes the impact.
  - Support vertical (role A vs role B) and horizontal (user 1 vs user 2 in the
    same role) checks, which means the client must supply at least two accounts
    per role — make that explicit in the intake form.

RATE LIMITING AND ABUSE-CONTROL TESTING

Two separate things, do not conflate them:

  1. Testing the TARGET's rate limiting (a security check):
     - measure requests accepted before throttling on: login, OTP request,
       password reset, signup, search, and any endpoint the policy marks
       `rateLimitSensitive`
     - detect header-based bypasses (X-Forwarded-For, X-Real-IP), method
       variation, case/path variation, and per-account versus per-IP scoping
     - HARD LIMITS: bounded attempt counts (default 20), a strict ceiling on
       requests per second, immediate stop on first throttle response, and an
       absolute ban on anything that could look like a flood. This check must
       never become a DoS. Enforce the ceiling in code, not in configuration
       alone.
     - never lock out real accounts: only run credential-adjacent rate checks
       against accounts the client has designated disposable

  2. OUR OWN outbound rate limiting (a safety control):
     - global and per-target requests-per-second caps, concurrency caps, and a
       jitter/backoff policy, all set in policy with safe defaults
     - adaptive throttling: watch target latency and 5xx rate; if either
       degrades past a threshold, back off automatically, and if it degrades
       further, abort the run and alert the tester
     - blackout windows (e.g. business hours) enforced by the scheduler
     - a `politeMode` for production targets that halves every limit

B8. SCAN MODULES

Every module follows the same contract: it declares its inputs, reads the
resolved policy, runs one or more pinned tool containers through the scope
guard, writes raw output to MinIO, parses to normalised findings, and reports
progress to the console. Adding a new tool must mean writing one adapter file,
nothing else.

B8.1 RECON AND ATTACK SURFACE
  Inputs: domains, wildcards, IPs, cloud accounts.
  Work: subdomain enumeration (passive and, if policy allows, active), DNS
  records, certificate transparency, HTTP probing and fingerprinting, port and
  service enumeration, TLS configuration, technology identification, exposed
  storage buckets, JavaScript endpoint and secret extraction, historical URLs,
  virtual host discovery.
  Output: an asset inventory that everything else consumes, plus findings for
  exposure issues (stale subdomains, expired certificates, exposed admin
  interfaces, missing DMARC/SPF/DKIM, information disclosure).

B8.2 WEB APPLICATION (UNAUTHENTICATED AND AUTHENTICATED)
  Work: crawling (browser-based, so SPAs are covered), ZAP baseline/full scans
  driven by the automation framework, nuclei template sets selected by the
  policy, TLS and header checks, cookie and CORS configuration, client-side
  issues, injection probing with non-destructive settings, file upload handling,
  and the access-control matrix from B7.
  Coverage must be expressible in WSTG identifiers so the report's coverage
  matrix is real and not decorative.

B8.3 API
  Work: OpenAPI/Swagger/Postman collection import; if none exists, build a spec
  from observed traffic. Schema-driven fuzzing, authentication and authorisation
  checks per endpoint, mass assignment, excessive data exposure, BOLA/BFLA
  probing, rate limiting, versioning and deprecated endpoint discovery, GraphQL
  introspection and query-depth abuse, JWT weaknesses (algorithm confusion,
  weak secrets against a wordlist, expiry and audience validation).
  Map to the OWASP API Security Top 10.

B8.4 MOBILE
  Work: MobSF static analysis of APK/IPA, manifest and permission review,
  hardcoded secrets, insecure storage, certificate pinning presence and bypass
  assessment, exported component review, runtime analysis via Frida/objection on
  an emulator, and traffic interception feeding the API module. Map to MASVS.
  Also produce a Play Store / App Store data-safety consistency check: does the
  declared data collection match what the binary actually does.

B8.5 CLOUD
  Work: read-only role assumption, prowler across the account with framework
  mappings, IAM privilege analysis, public exposure detection (storage, disks,
  snapshots, databases), logging and monitoring gaps, encryption at rest and in
  transit, network exposure, key rotation, and a cost-safe posture summary.
  Kubernetes: kube-bench and kubescape where a cluster is in scope.
  Cloud runs are read-only by construction — no write API call is ever made.

B8.6 CODE AND SUPPLY CHAIN (when the client grants repository access)
  Work: semgrep with curated rule packs, secret scanning across history, SBOM
  generation, dependency vulnerability analysis, IaC misconfiguration scanning,
  CI/CD configuration review, and a check for exposed pipeline secrets.

B8.7 NETWORK
  Work: nmap with safe script categories, service version identification, CVE
  correlation, default-credential checks against a conservative list, and
  exposure summarisation. No exploitation, no brute force beyond a tiny
  documented set, no DoS scripts — ever.

B8.8 LLM / AI RED TEAMING MODULE (build this to be genuinely excellent)

This is Attestor's differentiator. Treat it as a first-class module, not an
add-on. It must be runnable STANDALONE — the owner must be able to run only the
LLM tests against only an LLM endpoint, with no web scan at all — and also as
an add-on to a web engagement.

  TARGET TYPES the module must support:
    - a raw model endpoint (OpenAI-compatible, Anthropic, Bedrock, Vertex,
      Azure OpenAI, self-hosted vLLM/Ollama)
    - a chat application behind a web UI (drive it with Playwright)
    - a RAG application with a document ingestion path
    - an agentic system with tool/function calling
    - a customer-facing bot embedded in a product (WhatsApp/web widget)

  CONFIGURATION the user provides:
    endpoint, auth (key/bearer/cookie/session), request and response shape
    (JSON path to the prompt field and the answer field), system prompt if
    known, declared guardrails, declared tools/functions, the intended purpose
    and the topics the bot is supposed to refuse, per-request cost estimate,
    and a hard token/spend budget for the whole run.

  TEST CATEGORIES (map every finding to the OWASP LLM Top 10 and record the
  mapping in the report):
    - Direct prompt injection: instruction override, role reassignment,
      delimiter and encoding attacks, multilingual and obfuscated payloads
    - Indirect prompt injection: payloads planted in documents, web pages,
      emails, file names, image alt text and API responses the model ingests —
      this is the highest-impact class for RAG and agent systems
    - Jailbreaks: single-turn, multi-turn escalation (Crescendo-style),
      tree-of-attacks-style adaptive refinement, persona and hypothetical
      framing, and encoded payloads
    - System prompt extraction and configuration leakage
    - Sensitive information disclosure: training data extraction, PII leakage,
      other users' data leakage, internal document leakage from RAG
    - Insecure output handling: model output rendered into HTML (XSS), into SQL,
      into shell, into a URL fetch (SSRF), into a file path
    - Excessive agency: can the model call a tool it should not, with arguments
      it should not, without confirmation; chained tool abuse; privilege
      escalation through tool composition
    - RAG-specific: document poisoning, retrieval manipulation, citation
      fabrication, cross-tenant retrieval leakage
    - Supply chain: model provenance, plugin/extension trust, unpinned model
      versions
    - Denial of wallet / cost abuse: unbounded output length, recursive
      prompting, expensive tool loops — measure the cost impact and report it in
      currency, but stop well before causing real spend damage and cap it hard
    - Guardrail bypass: does the declared filter actually hold under the above
    - Hallucination and misinformation in a business-critical path (where the
      answer is used for a decision — pricing, eligibility, medical, legal)
    - Bias and toxicity where relevant to the client's risk posture
    - Agent-specific: goal hijacking, memory poisoning, inter-agent trust abuse,
      unsafe autonomous action

  TOOLING: orchestrate garak (broad probe sweep), promptfoo (YAML-defined
  adversarial suites and graded assertions in CI), PyRIT (multi-turn adaptive
  campaigns), deepteam (OWASP-LLM-mapped vulnerability coverage), plus a custom
  probe corpus stored in the repo as versioned YAML so Attestor can add its own
  payloads over time. Search for each tool's current interface before wiring.

  SCORING: an LLM finding needs a different treatment from a CVE. Record attack
  success rate over N attempts, reproducibility, the exact conversation
  transcript as evidence, the business impact of the successful bypass, and a
  severity that reflects real exploitability rather than a scanner's opinion.
  Keep full transcripts as evidence objects.

  SAFETY: never run cost-abuse tests without an explicit budget ceiling and
  client acknowledgement. Never leave a poisoned document in a client's
  production RAG corpus — track every artefact injected and remove it in a
  teardown step, then verify removal.

B8.9 AI-ASSISTED AND AGENTIC TESTING (optional, guarded, off by default)

  Two separate capabilities, never conflated:

  1. AI ASSIST (report and triage help) — enabled per engagement:
     - drafts finding descriptions, remediation text and executive summary
       prose FROM captured evidence only
     - proposes deduplication and correlation across tools
     - suggests a CVSS vector with a written rationale
     - explains a tool's raw output in plain language for the tester
     HARD RULES: it may never assert a fact not present in the evidence; every
     generated block is marked as draft in the UI and requires human approval
     before it can enter a report; the model sees redacted content only; the
     prompt and model version used are recorded with the finding for
     defensibility.

  2. AGENTIC TESTING (an autonomous agent like Strix) — off unless explicitly
     enabled per engagement:
     - runs only inside the scope guard, in an isolated container with egress
       restricted to in-scope resolved IPs
     - hard token/spend budget and wall-clock limit, both enforced by the runner
     - forbidden action list enforced at the proxy layer, not by asking the
       model nicely: no destructive HTTP methods on flagged endpoints, no
       out-of-scope hosts, no DoS patterns, no credential changes
     - every action logged to auditLog with the full request
     - all output enters the human review queue as CANDIDATES, never as
       findings
     Rationale for the tester: agents are good at breadth on day one and are
     structurally unable to find multi-role business-logic flaws. Budget them
     accordingly.

B9. CUSTOMISATION MODEL — POLICY AS CODE

Everything the owner asked to be customisable is expressed in a single YAML
policy, validated with a schema, resolvable in layers: global defaults →
client override → engagement override → single-run override from the console.
The console has a form for the common knobs and a raw YAML editor with schema
validation and a diff view for everything else.

The policy must be able to express, at minimum:

  modules:            which modules run (recon, web, api, mobile, cloud, code,
                      network, llm, agentic) — any subset, including "llm only"
  checks:             include/exclude individual checks by id, by WSTG id, by
                      ASVS requirement, by nuclei tag/severity, by OWASP
                      category. Both allowlist and denylist styles.
  intensity:          safe | standard | thorough — controls crawl depth,
                      payload sets, fuzz iterations, timeouts
  phases:             preLogin, postLogin, or both
  authProfiles:       which credential sets map to which roles
  accessControlMatrix: which role pairs to test, which id fields to mutate
  rateLimits:         global rps, per-target rps, concurrency, backoff,
                      politeMode, adaptive-abort thresholds
  windows:            allowed test windows in the client's timezone, blackouts
  readOnlyMode:       suppress all state-changing requests
  forbiddenActions:   url patterns and form actions never to touch
  exclusions:         paths, parameters, hosts, file types
  llm:                target config, probe packs, attempt counts, budget cap,
                      teardown behaviour
  ai:                 aiAssistEnabled, agenticEnabled, model, token ceiling
  evidence:           what to capture, masking rules, retention days
  report:             template id, branding, cvss version, compliance mappings
                      to include, sections to include or omit, tone
  notifications:      severity thresholds, channels, out-of-band alert rules

Ship 5 ready-made profiles: `quick-external`, `standard-web-app`,
`deep-web-app`, `cloud-review`, `llm-only`. The owner should be able to run a
complete engagement by picking a profile and changing two lines.

B10. SAFETY CONTROLS (collected, because they must be reviewable in one place)

  - Pre-flight checklist enforced before `running`: authorisation valid, window
    open, credentials verified, client emergency contact recorded, backup
    confirmation received for intrusive runs, WAF allowlisting confirmed or
    consciously skipped, production-versus-staging acknowledged.
  - Global and per-engagement kill switch.
  - Adaptive abort on target degradation.
  - Absolute prohibition on DoS-shaped traffic, enforced in the request layer.
  - Destructive-method guard: DELETE/PUT/PATCH on unknown endpoints require the
    policy to opt in, and are blocked entirely in readOnlyMode.
  - A dry-run mode that shows exactly which targets and checks WOULD run,
    without sending a packet. The owner should use this on every new engagement.

B11. FINDINGS PIPELINE

  - One adapter per tool converts raw output into the normalised finding model.
    Adapters are pure functions over a fixture file — that is what makes them
    testable.
  - Deduplication by a stable `dedupeKey` (rule id + normalised asset +
    normalised location + parameter), surviving across runs and across tools
    that find the same thing.
  - Correlation: group related findings into one reportable issue where the
    root cause is shared (one missing header across 40 endpoints is ONE finding
    with 40 affected assets, not 40 findings — this single behaviour is what
    separates a professional report from scanner output).
  - Severity: CVSS 4.0 and 3.1 both supported, chosen per engagement. Always
    store the vector string, not just the number. Allow a human severity
    override with a mandatory written justification — auditors ask for it.
  - False-positive memory per client: marking a finding false-positive
    suppresses that dedupeKey in future runs for that client, with the reason
    recorded and visible.
  - Manual findings: a first-class editor with the same fields, evidence
    attachment, and markdown support. The human's findings are the valuable
    ones; the UI must make entering them fast, not an afterthought.
  - Review queue: everything from scanners and agents lands as `candidate` and
    requires human confirmation before it can appear in a report. Bulk triage
    with keyboard shortcuts.
  - Status tracking across the retest cycle: open → fixed → riskAccepted, with
    dates, so the retest report writes itself.

B12. EVIDENCE HANDLING

  - Capture: HTTP request/response pairs, screenshots, terminal output, DOM
    snapshots, LLM conversation transcripts, tool raw output. Each object gets
    a sha256 for integrity.
  - Masking at capture time: configurable regex and field rules for emails,
    phone numbers, PAN/Aadhaar-shaped strings, card numbers, tokens, and any
    client-specified pattern. Store masked; never store the raw personal data.
  - Encryption at rest in MinIO; access only through signed short-lived URLs
    issued by the API after an authorisation check.
  - Retention: per-engagement retention days (default 90). A scheduled job
    purges expired evidence, writes the purge to auditLog, and generates a
    signed deletion confirmation PDF for the client.
  - Legal hold flag that suspends purging when an engagement is disputed.

B13. THE REPORT — SPECIFICATION

The report is the product. It must look like a document produced by a senior
consultant at a firm charging a serious fee, not like a tool export and not
like AI output. Study several published sample reports from established firms
before designing the template.

DELIVERABLES

  1. Full assessment report (PDF + HTML)
  2. Retest report (PDF) showing fixed / open / accepted with dates
  3. One-page attestation letter (PDF) — the artefact the client forwards to
     their enterprise buyer or auditor
  4. Optional executive one-pager for a board

SECTION ORDER FOR THE FULL REPORT

  1.  Cover — client name, engagement title, report version, date range,
      classification (CONFIDENTIAL), Attestor wordmark, document reference id
  2.  Document control — version history, author, reviewer, distribution list,
      handling instructions, confidentiality statement
  3.  Executive summary (2–4 pages, no jargon) — what was tested, why, the
      headline risks in business terms, the overall posture rating, the count
      by severity, what changed since the previous assessment if there was one,
      and the three things to do first
  4.  Risk overview — severity distribution, findings by category, findings by
      asset, and a remediation-priority view. Charts must be legible in
      greyscale print.
  5.  Scope — assets in scope, assets explicitly out of scope, environments,
      test dates and times, roles and accounts used, test type (black/grey/
      white box), any client-imposed constraints
  6.  Methodology — named standards (OWASP WSTG, ASVS 5.0, Top 10:2025, API
      Top 10, MASVS, LLM Top 10, NIST SP 800-115, PTES), the phase structure,
      the tools used with versions, and the severity model with the CVSS
      version used
  7.  Coverage matrix — every methodology category, marked tested / partially
      tested / not tested, with a reason for anything not fully tested. This
      section is what protects the firm when something is missed, and what
      auditors look for. It must be generated from what actually ran, never
      hand-waved.
  8.  Attack narrative — a written walkthrough of the most significant chain:
      how a low-severity information disclosure plus a weak access control
      became a critical outcome. This section is the single biggest quality
      differentiator between a cheap report and an expensive one. Support it
      with a step diagram.
  9.  Detailed findings — one per issue, ordered by severity then by asset:
        finding id (stable, quotable, e.g. ATT-2026-014-003)
        title (specific: "Order history of any user retrievable by changing
               orderId", not "IDOR vulnerability")
        severity + CVSS vector string + score + version
        CWE id, OWASP category, WSTG id, ASVS requirement
        affected assets / endpoints / parameters
        business impact in plain language, quantified where possible
        likelihood and attacker prerequisites
        technical description
        reproduction steps, numbered, precise enough for a developer to repeat
        evidence: request/response excerpts (masked), screenshots, transcripts
        remediation: specific to the client's stack, with code or configuration
                     the developer can apply — never "sanitise all input"
        references: OWASP cheat sheet, vendor docs, CVE where applicable
        status and retest result
  10. Positive observations — controls found to be working. Real ones. This
      builds credibility and is standard in senior reports.
  11. Strategic recommendations — a prioritised 30 / 60 / 90 day roadmap,
      grouped by root cause rather than by finding
  12. Compliance mapping appendix — findings mapped to ISO 27001:2022 A.8.8 and
      related controls, SOC 2 Trust Services Criteria, PCI DSS 4.0 req. 11.4,
      DPDP reasonable security safeguards, and OWASP ASVS levels. Configurable
      per engagement.
  13. Appendices — tool inventory with versions, full port/service tables, the
      complete asset inventory, out-of-scope notes, glossary, and the
      limitations and disclaimer statement
  14. Limitations and disclaimer — use the drafted text in PART G1 verbatim.
      Point-in-time, scope-limited, no guarantee of the absence of
      vulnerabilities, no certification, no third-party reliance, liability
      capped at fees. It appears on every assessment and retest report, is
      version-pinned per issued document, and must not be removable by the UI.
      The cover classification statement is PART G2 and the retest scope
      statement is PART G4.

VISUAL DESIGN OF THE REPORT

  - Print-first CSS. A4 and US Letter. Correct page breaks — a finding never
    splits awkwardly across a page boundary; evidence blocks stay with their
    finding.
  - Running header with client name and classification; running footer with
    "Page X of Y", document reference and version.
  - Serif for body text, grotesk for headings and tables, mono for evidence.
    Consistent severity colours used sparingly, and distinguishable in
    greyscale.
  - Tables with real typography — aligned numerals, no zebra stripes, thin
    rules.
  - A generated table of contents with page numbers, and bookmarks in the PDF.
  - No emoji, no icon clipart, no gradients, no stock imagery.
  - Client logo optional, Attestor wordmark always.

WRITING RULES (enforce in the AI-assist prompts and in the review checklist)

  - No filler openings, no "In today's threat landscape", no "it is important
    to note that", no exclamation marks, no marketing adjectives.
  - Every claim traceable to evidence in the report.
  - Active voice, past tense for what was done, present tense for what is true.
  - Consistent terminology — one term per concept throughout.
  - British or American spelling chosen once and enforced.
  - Numbers, versions and endpoints exact. Never approximate a technical detail.

REPORT TEMPLATING

  - Templates are HTML + CSS in the repo, versioned, with a template id stored
    on each report so an old report can be re-rendered exactly.
  - Content comes from the findings database; prose blocks are editable in the
    console with markdown, and edits are stored, not regenerated.
  - A pre-release review checklist blocks release until: every finding has
    evidence, every finding has remediation, no placeholder text remains, the
    coverage matrix is complete, the disclaimer is present, the client name
    appears correctly everywhere, and a human has ticked "I have read every
    line of this report".

B14. CLIENT PORTAL — SHIPS IN V1, NOT DEFERRED

The portal is part of the first release. It is the difference between handing
over a PDF and running a service: it is where the client watches remediation
progress, requests the retest, and renews the retainer. Build it properly.

It is also the ONLY publicly reachable surface of the platform, so it is a
separate deployment with its own hardened, minimal, read-mostly API. It must
never share a process, a port or a database role with the internal console.

B14.1 ACCESS AND ACCOUNTS

  - Client users are created by invitation from the console only. No public
    signup, no password reset that can enumerate accounts, no open registration
    endpoint of any kind.
  - Invitation flow: tester invites an email address and assigns a role; the
    invitee receives a single-use, expiring link (48 hours); they set a password
    (argon2id) and are required to enrol TOTP MFA before first access. MFA is
    mandatory for every client user without exception — this account can see
    unfixed vulnerabilities in their production systems.
  - Client roles:
      clientOwner    sees everything for their organisation, manages their own
                     users, downloads reports
      clientMember   sees assigned engagements, can update finding status and
                     comment, cannot manage users
      clientViewer   read-only, cannot download reports
  - Scoping is enforced server-side on every single route by clientId derived
    from the session, never from a request parameter. Write an integration test
    per route that asserts client A cannot read client B's data by id
    substitution. This is the exact bug class Attestor sells testing for; the
    portal must not have it.
  - Sessions: short-lived, rotated on privilege change, invalidated on password
    change, with a visible active-session list and a "sign out everywhere"
    action.
  - Access revocation is immediate: when a tester deactivates a client user or
    an engagement is closed, existing sessions and any outstanding signed URLs
    are invalidated in the same transaction.

B14.2 PAGES AND FUNCTIONALITY

  Dashboard
    - Current posture: open findings by severity, trend since last assessment,
      oldest unresolved critical, next scheduled scan (retainer clients).
    - Active engagement status with the lifecycle stage shown in plain language
      ("testing in progress", "report in preparation", "awaiting your retest
      request") — never internal state names.
    - Outstanding actions for the client, listed explicitly.

  Engagements
    - List of their engagements with type, dates, status, deliverables.
    - Engagement detail: scope summary, methodology and standards used, test
      window, roles tested, and the deliverable downloads.

  Findings
    - Filter and sort by severity, status, asset, category, first-seen date.
    - Finding detail: everything in the report finding block — description,
      business impact, reproduction steps, evidence, remediation, references,
      CVSS vector and score, standard mappings.
    - Evidence rendered inline as INERT TEXT and images. Captured HTTP bodies
      and LLM transcripts are never rendered as live HTML. Sandbox the viewer
      (iframe with a restrictive sandbox attribute plus CSP) — an XSS here would
      be an XSS delivered by the security vendor.
    - Client-settable status: acknowledged, in progress, fixed (pending
      verification), risk accepted. Risk accepted requires a written
      justification and records who accepted it and when — that record is
      itself an audit artefact the client will need later.
    - Comment thread per finding, threaded between client and tester, with
      email notification to the other party. Markdown supported, sanitised on
      render, no file attachments from the client side in v1.
    - "Mark all fixed and request retest" bulk action.

  Retest
    - A single prominent action: "Request retest". It creates a retest job in
      the console, records the requested date, and shows the client which
      findings will be re-verified.
    - Retest eligibility and remaining free-retest window shown clearly
      (one free retest within 30 days of report release; after that it is a
      paid engagement — state this, do not let it become a dispute).
    - Retest results appear as a diff: verified fixed, still open, regressed.

  Reports and documents
    - Assessment report, retest report, attestation letter, and the evidence
      deletion confirmation, each with version and release date.
    - Downloads are watermarked per download with the recipient's name, email,
      organisation and UTC timestamp on every page. Watermarking happens at
      download time, server-side, not at render time.
    - Downloads are served through short-lived signed URLs (5 minutes,
      single-use), and every download is written to auditLog with user, IP and
      user agent.
    - clientViewer role cannot download, only read in the browser.
    - An HTML view of the report inside the portal so a client can read it
      without downloading anything.

  Assets and coverage
    - What was in scope, what was explicitly out of scope, and the coverage
      matrix from the report. Clients ask "did you test X?" constantly; answer
      it once, in the product.

  Continuous monitoring (retainer clients)
    - Timeline of scheduled runs, new findings since last run, resolved
      findings, and regressions flagged prominently.
    - Attack-surface changes: new subdomains, new open ports, certificate
      expiries approaching, exposed secrets detected.
    - Monthly posture summaries, downloadable.

  Security questionnaire helper
    - A library of standard, reusable answers describing Attestor's testing
      process, methodology, tester independence, data handling and retention —
      written so the client can paste them into their own buyer questionnaires.
    - Copy-to-clipboard per answer, and an export of the whole set.
    - This is a small feature that generates a disproportionate amount of
      goodwill and referrals. Do not skip it.

  Account
    - Profile, password change, MFA management, active sessions, notification
      preferences, and their organisation's user list (clientOwner only).

B14.3 NOTIFICATIONS TO CLIENTS

  - Email on: report released, retest complete, comment reply, new critical or
    high finding from a continuous run, scheduled scan starting (retainer),
    and evidence deletion completed.
  - Every client-facing email is queued for human review and release in v1.
    Nothing is auto-sent. The only exception the owner may later enable is the
    scheduled-scan-starting notice.
  - Notification preferences per user, with severity threshold.
  - Emails contain no findings detail — a link to the portal only. Never put a
    vulnerability description in an email body.

B14.4 PORTAL SECURITY REQUIREMENTS

  - Separate deployment, separate container, separate database credentials with
    a least-privilege role that cannot read other clients' rows, cannot read the
    credential vault at all, and has no write access to auditLog beyond append.
  - The portal API exposes only the routes it needs. It must not import the
    console's route modules.
  - Strict CSP, CSRF protection on all state-changing routes, HSTS with
    preload, secure/httpOnly/sameSite cookies, and rate limiting on
    authentication routes with account lockout backoff that does not enumerate
    users.
  - No credential vault access, no scan control, no policy editing, no ability
    to trigger a tool run from the portal. The retest request creates a request
    record only; a human starts the job.
  - All uploads disabled. Clients cannot upload files in v1.
  - Every action written to auditLog with actor, IP, user agent, and subject.
  - Include the portal in the platform's own ASVS 5.0 self-assessment at M13,
    and treat any finding in it as a release blocker.

B14.5 PORTAL ACCEPTANCE CRITERIA

  - A client user can log in, read every finding, update status, comment,
    request a retest, and download a watermarked report — without the tester
    doing anything manually.
  - Client A cannot reach any object belonging to client B by any id, filter,
    export or signed URL. Automated tests prove it per route.
  - Revoking a user kills their session and their outstanding signed URLs
    immediately.
  - Evidence rendering cannot execute script under any captured payload,
    including stored XSS payloads found during the engagement. Test this with a
    real payload corpus.
  - The portal works with JavaScript-heavy interactions on mobile, since
    founders read these on phones.

B15. CONTINUOUS / RETAINER ENGINE

  - Repeatable scheduled runs per client, per module, honouring test windows.
  - Diff engine: new findings, resolved findings, regressions (a previously
    fixed dedupeKey reappearing — flag these loudly, they signal a broken
    deployment process and they sell the retainer better than anything).
  - Attack-surface monitoring: new subdomains, new open ports, new services,
    certificate expiry, DNS changes, exposed secrets appearing in public
    repositories.
  - Monthly one-page posture summary generated and queued for human review
    before sending.
  - SLA timers on open critical and high findings, with escalation reminders.

B16. NOTIFICATIONS AND INTEGRATIONS

  - Out-of-band critical alert: when a critical finding is confirmed, notify
    the tester immediately and prepare a pre-written client notification for
    human sending. Never auto-send to the client.
  - Email (SMTP/Resend), and optional Slack/Teams webhooks for the tester.
  - Export formats: JSON, CSV, SARIF, and a DefectDojo-compatible import so a
    client with existing tooling can ingest results.
  - Optional Jira/Linear issue creation from a confirmed finding, with the
    remediation text and evidence link.
  - Invoicing stays outside the system — record amounts and payment state only,
    and export a CSV for the accountant. Do not build accounting.

B17. COST CONTROL

  - Single VPS to start: 4 vCPU / 8–16GB RAM / 160GB SSD is sufficient for the
    full stack plus tool containers. Document the sizing in the runbook.
  - Per-client scanning VPS with a fixed egress IP is a deployment option, not
    a code change — the runner takes an egress profile.
  - Tool images cached locally and pinned by digest; never pull latest at run
    time.
  - LLM spend: hard per-engagement token budget, a cheaper model for bulk
    triage and a stronger one only for report prose, prompt caching where the
    provider supports it, and a running cost display in the console. The whole
    AI layer must be switchable off with one config flag and the system must
    remain fully functional without it.
  - No paid SaaS anywhere in the critical path. Everything self-hosted or free
    tier, with the swap-in point documented if the firm later pays for
    something.

B18. SECURITY OF THE PLATFORM ITSELF

This system holds client credentials and evidence of client vulnerabilities. It
is the highest-value target the firm will ever operate. Treat it accordingly and
write `docs/THREAT-MODEL.md` covering all of this:

  - Console and internal API never exposed to the public internet: bind to a
    private interface and reach them over WireGuard/Tailscale. The client
    portal (B14) is the ONLY public surface, ships in v1, and is a separate
    deployment with a minimal, read-mostly API and its own least-privilege
    database role. Everything in B14.4 is mandatory, not aspirational.
  - Mandatory TOTP MFA for staff accounts. Argon2id password hashing. Short
    sessions, rotation on privilege change.
  - Strict role separation: owner, tester, client. Least privilege enforced
    server-side on every route, never in the UI only.
  - Append-only audit log; nothing in the app can edit or delete it.
  - Encrypted backups, off-box, restore-tested, with the restore procedure in
    the runbook.
  - All tool containers run non-root, read-only root filesystem where possible,
    dropped capabilities, no host network, per-run network namespace, resource
    limits, and a wall-clock timeout.
  - Dependencies pinned with a lockfile; CI runs a vulnerability scan on the
    platform's own dependencies and container images.
  - Secrets from environment/KMS only; a pre-commit hook and CI check that
    blocks committed secrets.
  - The platform's own security headers, CSRF protection, and strict input
    validation — an XSS in a findings viewer that renders attacker-controlled
    response bodies is a real and obvious risk. Sanitise and sandbox all
    rendered evidence; render captured HTTP bodies as inert text, never as
    live HTML.

B19. TESTING STRATEGY

  - Unit: policy resolution, dedupe keys, CVSS parsing, severity mapping,
    redaction filter, masking rules, adapter parsers against fixture files.
  - Property/fuzz: scope guard (wildcards, unicode domains, suffix tricks,
    DNS rebinding shapes, IPv6, redirect chains). This suite must be thorough.
  - Integration: full engagement run against the local vulnerable stack
    (Juice Shop, DVWA, WebGoat, VAmPI, crAPI, plus a purpose-built vulnerable
    LLM app you write for the LLM module). Assert that known-planted issues are
    found and that no request ever leaves the test network.
  - Golden-file: report HTML rendering from a fixed findings fixture.
  - E2E: Playwright through the console — create engagement, upload
    authorisation, add scope, add credentials, run, triage, generate report,
    release.
  - Negative tests: attempts to run without authorisation, outside the window,
    against an excluded host, after revocation — all must fail closed.
  - CI must never make an outbound connection to a real target.

B20. DEPLOYMENT AND OPERATIONS

  - `docker compose up` brings up the entire stack locally including test
    targets, with seeded demo data and a demo engagement so the owner can see
    the whole flow in five minutes.
  - Production compose file with resource limits, restart policies, log
    rotation and healthchecks.
  - Migrations run on deploy, reversible, checked in.
  - `docs/RUNBOOK.md`: VPS provisioning, DNS and egress IP setup, backup and
    restore, key rotation, adding a new tool adapter, adding a report template,
    the panic-stop procedure, and the client-onboarding checklist.
  - Structured JSON logs through the redaction filter; simple metrics
    (jobs queued/running/failed, run duration, findings per run, token spend).

B21. PLATFORM ACCEPTANCE CRITERIA

  - A complete engagement can be run end to end from the console without
    touching a terminal.
  - "LLM only" and "cloud only" engagements run with no web scanning at all.
  - Attempting any action against an unauthorised, excluded or out-of-window
    target fails closed, logs, and explains which rule stopped it.
  - Credentials never appear in any log, any UI surface, any report or any
    exported file.
  - A report generated from the demo data is genuinely presentable to a paying
    client without editing anything except the client-specific prose.
  - Turning off the AI layer entirely leaves the system fully functional.
  - Every module is configurable from the policy without a code change.
  - Test suite green; scope guard property tests included.

This is the highest density of real findings per hour in the whole business, and it is the easiest
engagement to approve internally, because it cannot break anything.

You give us a role with read permissions. We assume it, enumerate every account, subscription,
project and region — including the ones nobody remembers — and check the configuration against the
benchmarks. Then we do the part the benchmark tools do not: work out which of those findings
actually chain into a path from a low-privileged identity to administrator.

## What comes back

Almost every small cloud account has the same four problems, and yours probably has at least two of
them: a storage bucket that is public because a support tool needed it in 2024, an IAM role that can
pass any role to a compute service and is therefore administrator by another name, access keys that
have not been rotated since the account was created, and management logging enabled in one region
only.

None of those is exotic. All of them are the reason cloud incidents look the way they do. We report
them with the exact command or console change that fixes each one, ordered by what actually reduces
risk rather than by what the benchmark numbers them.

## The read-only guarantee is structural

The role you grant has no write permissions, and the platform that runs the review has no code path
that issues a write API call. This is not a promise about our carefulness; it is a property of what
we built. If you want to verify it, the role policy we ask for is the artefact — read it before you
create it.

## Kubernetes

If a cluster is in scope we add benchmark checks against the control plane and nodes, an RBAC review
looking for the paths from a pod to cluster administrator, and a check on network policy and pod
security standards. The most common finding is that there is no network policy at all, which means
every pod can reach every other pod and the metadata endpoint — and that turns any single pod
compromise into a cluster compromise.

## Where this fits

Buy it on its own when your infrastructure has outgrown the person who set it up. Buy it alongside a
web application audit when the application and the account belong to the same risk conversation,
which they usually do: an SSRF in the application plus an unprotected metadata endpoint is one
finding in the report and two teams in the room.
